## 2. What was found before building

Measured, not assumed:

- **The Word Card could not appear in the Note view because its mount lived
  inside `#readView`.** One mount, one view.
- **The Note view's own Word-by-Word panel was built without interactivity.**
  The Read view calls `renderWordByWordPanel(..., { interactive: true, surahNumber })`;
  the Note view called it with neither. That single missing pair of options is
  the whole reason a word was tappable in READ and inert in NOTE.
- **Occurrences were inert text** — `<li>2:255:3</li>`, no control.
- **The app already had a drag-and-resize window system.** `initPopupWindow()`
  in `app/js/note-popup.js` already does drag-by-handle, resize from all eight
  edges and corners, viewport clamping, per-window remembered geometry, and a
  clean fall back to plain flow below 900px. The Note, Approach and Explore
  views all use it. **Request 3 was therefore a reuse job, not a new system.**

## 3. What was built

### 3.1 The Word Card works in the Note view

A second mount, `#quranWordCardMountNote`, sits in `#noteView` as a **sibling
of `#notePopupBody`** — deliberately *outside* `#noteViewMount`.

That placement is the whole guarantee for "preserve note text and editing
state". `renderNoteViewNow()` replaces `#noteViewMount`'s innerHTML on every
render, and the note editor (`[data-note-editor]`, a contenteditable) lives
inside it. Because the card mount is outside that element, **opening, closing,
retabbing or moving the card never re-enters the note render path at all.**
This is a structural guarantee, not a save-and-restore dance — and the checks
prove it by asserting the editor is the *same DOM node* before and after.

The Read view's mount and the Note view's mount share one set of handlers.
Neither view is named inside them: every lookup goes through
`activeWordCardMount()`.

### 3.2 Each Basic Arabic occurrence is clickable

Every root-linked and lemma-linked occurrence is now a real `<button>`
carrying `data-word-occurrence-goto`, which holds the same permanent
occurrence identity (ADR-007) the card itself is keyed by — never a label to
be re-parsed.

Clicking one loads that surah if needed, moves to that āyah, and opens the
card on that exact word.

**The way back** is a bar in the card reading "Visiting from 2:255:3" with a
"↩ 2:255:3" button. It restores the original word *and* the study context —
surah, āyah, unit type, and which stage view the reader was in. Only the
**first** hop records an origin, so a chain of jumps still offers the way back
to where the reader actually started, not to the previous hop.

**Following an occurrence out of the Note view opens the destination in the
READ view.** This is deliberate: the Note view is showing one āyah's note, and
quietly re-pointing it at a different āyah would rebuild its contenteditable
and take unsaved text with it. Switching stage view only toggles `hidden`, so
the note's DOM — text and all — is still intact when "back" returns to it.

### 3.3 Desktop drag and resize

At ≥900px both mounts become floating windows through the **existing**
`initPopupWindow()`, at the same breakpoint the Note, Approach and Explore
views already use. Below 900px none of it applies and the card is the docked
strip it has been since Phase 2 — no inline geometry is written at all.

Two additive options were added to the shared module; **both default to the
existing values, so all four existing call sites are behaviourally
unchanged:**

- `minWidth` / `minHeight` — the card floats to a **320×240** floor instead of
  the stage views' 480×360. It is a card, not a stage view, and 480×360 is
  most of a laptop's height for three lines of Arabic.
- `dragFromSelector` — the card's header is rewritten on every tab switch, so
  it cannot *be* the handle (a listener bound to replaced markup dies with
  it). The static mount is the handle and this selector keeps drags to the
  header.

Each mount has its own remembered geometry, so moving the Read view's card
never shoves the Note view's one. The card cannot be dragged off-screen.

## 4. Two real defects found by measuring

Both were in this round's own work, and both were caught by checks rather than
by reading the code.

**(1) The occurrence buttons were too small.** They shipped at 32px against
`quran-word-card-rendered.mjs`'s own ≥36px tap-target rule, which failed
across 12 viewport/language combinations. Raised to **40px**, this project's
own standing target for anything a finger presses, so they match the card's
other controls rather than merely clearing the bar.

**(2) The south edge could not be resized.** Corners and the east edge worked;
the south edge did nothing. The cause was the mount's inherited
`overflow-y: auto`, which **clipped the resize handles** — they sit
deliberately 3px outside the box. The window must not scroll; its content
does. Fixed with `overflow: visible` on the window and the scroll moved to
`.word-card-content`. A screenshot would never have shown this.

## 7. What the Owner should test

Open **https://madrasatul-muslimeen.github.io/app/** → **Quran Study**. Check
the badge reads **v08.20** (hard-refresh if it still says 08.19).

**1 — The Word Card in the Note view**
Open **Study options** → tick **Word by Word**. Tap the **⋮** on an āyah →
**Note & more**. In the Note screen, type something into the note box, then
tap an Arabic word.
*Expect:* the Word Card opens inside the Note screen, and **your typed note
text is still exactly where you left it**. Close the card — the text is still
there.

**2 — Clickable occurrences**
With the card open, tap **Basic Arabic**. Under the root and lemma counts you
will see a row of reference buttons (like `2:19:4`). Tap one.
*Expect:* the app moves to that place in the Qur'an and opens the card on that
word. A bar appears reading **"Visiting from …"** with a **↩** button naming
the word you came from. Tap it.
*Expect:* you are returned to the original word and the screen you were on,
and the "Visiting from" bar disappears.

**3 — Drag and resize (desktop/laptop only)**
On a computer, open a Word Card. Drag it by its **header** (the row with the
Arabic word and the ‹ › × buttons).
*Expect:* the card moves. Now drag any **edge or corner**.
*Expect:* it resizes from all eight, it will not shrink below a usable size,
and it cannot be pushed off the screen. On a phone or tablet nothing changes —
the card stays the strip along the bottom.
