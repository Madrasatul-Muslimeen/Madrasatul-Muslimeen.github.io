## What was built

All work lives under two new, Health-owned, nonprotected paths — nothing
outside them was touched:

- `app/health/` — the module foundation (data, selectors, view, page, and
  this tranche's own `README.md`, which is the fuller technical account;
  this report is the dated summary).
- `tools/health-atlas-verify/` — three focused, dependency-free Node test
  suites plus the verified-source fixture they check against.

**Data preservation** (`app/health/js/health-atlas-data.js`): every system,
organ, food, disease, lifestyle habit, age group, food master-category and
reference — 9 / 46 / 34 / 17 / 10 / 6 / 8 / 8, exactly the counts the issue
itself states — re-derived directly from the verified commit (not retyped by
hand) and compared byte-for-byte against a fixture pulled from that same
commit. `HEALTH_ATLAS_STATUS` is the literal string `'DRAFT'`, and
`HEALTH_ATLAS_PROVENANCE` carries the branch/commit/blob/hash/byte-length
above as exported constants a test binds against, so a future edit that
silently changes the data or its provenance record fails a check rather
than going unnoticed.

**One concrete working capability**: a read-only Body Systems browser
(`app/health/health-atlas.html` + `js/health-atlas-view.js`). Pick a system,
see its organs; pick an organ, see its name, its body system, its
**functions** (what it does), what it connects to, and links to the
general references the source itself cites — each screen carrying a DRAFT /
"not medical advice, consult a qualified professional" notice. Verified
running, not just asserted: a focused, un-checked-in Playwright script
(served locally via this repo's own `serve.js`, the same way every other
page under `app/` already needs to be run) found all 9 system blocks, opened
Heart, read back its 4 functions and 4 resolved references, and returned to
the list — screenshotted at both steps, no page errors.

**What this tranche deliberately did not build.** The source also carries
per-organ `nutritionNeeds`/`foodSources`/`activity`/`deterioration` (several
with specific figures, e.g. a milligrams-per-day amount) and per-disease
`remedies`/`homeRemedies`/`naturalRemedies`. The task instruction is explicit
about not showing these as per-fact verified or as organ-specific additive
doses. Rather than paraphrase or soften them, this tranche **preserves that
data in the data file but never renders it** — the view module reads only
`functions`, `connections` and `refs`, and never imports the Foods,
Diseases, Lifestyles or Ages datasets at all. That boundary is enforced
mechanically, not just by convention: `tools/health-atlas-verify/
view-boundary.mjs` reads the view module's own source text (comments
stripped first, so its own explanatory prose naming the deferred fields
doesn't trip itself) and fails if any of those fields or datasets are
referenced in executable code. Proven able to fail: a one-line mutation
adding `organ.remedies` to the view module was caught (13 passed / 1 failed,
naming exactly the leaked field) and reverted before anything was committed.

Also deferred, and named as the proposed next tranche below: the Foods /
Diseases / Lifestyle / Age Groups tabs, the wheel/diagram visualisation,
edit/import/export, and language-keying (I11) — this page is English-only
and unlinked from any nav, matching how other demo-only draft surfaces in
this repository have been staged before a translation and product-fit pass.

## A real finding, corrected rather than shipped silently

The task called for a "standalone-capable" foundation. The first draft's own
page copy claimed it could be opened directly with no server — untrue, and
caught by measuring rather than assuming: a Playwright run against a bare
`file://` path failed outright, with the browser's console naming the exact
cause — `Access to script … has been blocked by CORS policy … only
supported for protocol schemes: chrome, …, http, https …` — because the
page's ES module imports (`<script type="module">`, importing the data,
selector and view files separately) are blocked by the browser under the
bare `file:` scheme. This is not unique to this page: `serve.js`'s own
header comment already says the whole `app/` tree needs a local server
rather than a double-clicked file, for exactly this class of reason. The
page copy and `README.md` were corrected before this report was written:
"standalone" here means no sign-in, no tenant, no backend, nothing
persisted — not "opens from a bare file path" — and the README now states
the one-line way to run it (`node serve.js`, then
`http://127.0.0.1:8080/app/health/health-atlas.html`). The same Playwright
run against that URL passed in full.

## A second real finding, corrected the same way

The first cut of the Node test suites loaded `app/health/js/*.js` via plain
dynamic `import()`, which needs a `package.json` declaring
`"type": "module"` in that directory for Node to parse a bare `.js` file as
ESM. Adding one was reverted after checking `.gitignore`: it ignores every
`package.json` in the repository except
`tools/firestore-emulator/package.json`, with its own comment recording why
— *"infrastructure; all other package manifests remain machine-local/
ignored."* That reads as a deliberate repository policy, not an oversight,
and `.gitignore` is exactly the kind of shared/root config this tranche's
own boundary rule ("no shared file changes") means to respect even though
it isn't one of the named protected files. The fix
(`tools/health-atlas-verify/import-esm-file.mjs`) loads each `.js` file as a
`data:` URL instead — Node's ESM loader treats that as a module regardless
of extension or any `package.json`, with no flag and no exception needed to
the ignore rule.

Three suites, all passing, run from the repository root:

| Suite | Result |
|---|---|
| `node tools/health-atlas-verify/data-integrity.mjs` | 21 passed, 0 failed |
| `node tools/health-atlas-verify/selectors.mjs` | 8 passed, 0 failed |
| `node tools/health-atlas-verify/view-boundary.mjs` | 14 passed, 0 failed |

`data-integrity.mjs` checks the ported dataset against the verified-source
fixture field by field, checks every id is unique within its entity array,
that every `organ.system` resolves to a real system, and that every `refs[]`
id across organs/foods/diseases/lifestyles resolves to a real reference.
`selectors.mjs` exercises the pure, DOM-free selector functions the view
module is built on. `view-boundary.mjs` is the deferral guard described
above, with its own positive control (asserting the view really does call
`getOrgan`/`referencesFor` and read `organ.functions`, so the guard cannot
pass by finding nothing at all).
