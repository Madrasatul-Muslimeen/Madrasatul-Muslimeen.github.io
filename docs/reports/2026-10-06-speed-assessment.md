# Speed assessment: why opening takes long (6 Oct 2026)

**The Owner, 6 Oct 2026:** "Assess and fix issues with speed, loading. opening of all files, modules takes ages."

Measured in this sandbox. The live site cannot be opened in a browser from here, because the sandbox's TLS
interception is refused, and loosening certificate checks was declined. So every number below comes from the
repository's own files on the local server, with:
- the processor slowed four to six times, to stand in for a phone;
- a simulated Firestore delay of 400 ms per trip (`latencyMs`).

GitHub Pages sends `cache-control: max-age=600` and gzip. Gzip makes every transfer about a quarter of the
sizes below.

## What was found

| # | Finding | Measured | Fixed in v09.94? |
|---|---|---|---|
| 1 | **Every release threw the on-device cache away.** `sw.js` named its cache after `APP_VERSION` and deleted the old one on activate. The first opens after each update re-downloaded every app file, the Qur'an text, the word indexes and the Hadith data, while the reader waited. Releases came several times a day (v09.84 to v09.93 in two days), so the cache was nearly always cold. | Main page: 112 files, 2.9 MB. First Word Card: 7 files, 2.1 MB (`lemmas-index` 718 KB, `roots-index` 441 KB, `lemma-dictionary-en` 402 KB, `lemma-meaning-index` 371 KB, …). Hadith page: 2.5 MB. | **Yes.** While the new version waits, it refreshes everything the old cache held into its own cache, with revalidating fetches: an unchanged file costs a "not modified" answer. The first open after "Updated — tap to reload" finds every file already on the phone. Proven by two new `service-worker.mjs` checks; both fail with the carry-over removed. |
| 2 | **The Hadith page loaded every OpenITI book's whole index (1.8 MB) to draw an 11-row list.** | Hadith page 2,493 KB → 1,085 KB. Collections 2.5 MB → 737 KB. | **Yes.** The list reads `split/books-summary.json` (2.6 KB, generated by `tools/hadith-data-pull/openiti-books-summary.mjs`). A book's index loads when that book is opened. `openiti-books-summary.mjs` fails if the summary drifts from the indexes. |
| 3 | The app's own code at startup is small. | Profiled at 4× slower CPU: about 0.25 s of script and parse on the main page. The rest is waiting. | Nothing to fix. |
| 4 | The landing wheel waits on about **3 Firestore round trips in sequence**: `userIndex`, then tenant, people and Approaches, then the records chunk and the surah. | At 400 ms per trip: ready at 1.65 s, against 0.46 s with no delay. | **Not yet.** It needs a paint from the device's last copy before the network answers (the load-speed contract's "paint immediately"). That is a design round, proposed below. |
| 5 | The main page imports **106 modules at startup**, including the Word Card, Depth, the note foundation and the Journey Map service. The landing does not need them. | 1.45 MB of script, about 400 KB gzipped. | **Not yet.** Loading them when first used would save about a third of the startup script. This is a careful round: many suites patch `quranrevival.html`. |
| 6 | The Hadith page still loads HadeethEnc's `categories.json` for ar and en (423 KB) to draw the category list. | 423 KB | **Not yet.** It is the same summary-file fix as item 2. |

## Proposed next rounds (in this order)
1. **Startup paint from the device's last copy** (item 4). This touches the startup path, so it is an I9 item
   and is said here first.
2. **Load the Word Card, Note and Journey modules only when first opened** (item 5).
3. **A small HadeethEnc category summary** (item 6).
