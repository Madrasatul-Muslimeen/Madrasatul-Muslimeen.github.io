## 3. Data semantics — the A–E report

Everything below is **measured across the whole packaged corpus** (114 surah
files, 77,429 words), not inferred. A checked-in test
(`the segment list matches the packaged corpus exactly`) re-derives the segment
set from the corpus on every run, so these numbers cannot drift silently.

### A. What uniquely identifies each written form

**`morphology.lemma`** — the dictionary/citation form. 4,832 distinct values
across 74,122 lemma-bearing occurrences (3,307 words carry no lemma).

This is the source's own identity key, not a convenience: where two different
words share a spelling the corpus disambiguates them *in the lemma string
itself* with a numeric suffix — `مَٰلِك` (Noun) and `مَٰلِك2` (Proper Noun) are
two entries under root `ملك`. Forms are therefore grouped by lemma and stay
grouped by lemma.

### B. What field supplies the grammatical / POS category

**`morphology.pos`**, and nothing else. Every word has one (0 missing).

It is not a single label. It is a `" + "`-joined chain describing the **whole
written token**: attached proclitics, then the head word, then any attached
pronoun — e.g. `Determiner + Noun`, `Conjunction + Verb + Pronoun`.

- **359** distinct `pos` strings
- built from exactly **46** distinct segments

The category **of the word itself** is the **head**: the last segment that is
not `Pronoun`. That rule is implemented once, in the index builder, and is
stated in the packaged file itself (`"headRule"`).

### C. Can one written form have multiple POS classifications?

**Yes, but rarely — and v08.21 got the size of this wrong.**

| Measure | Count | Share |
|---|---|---|
| Lemmas with more than one **raw `pos` string** | 2,067 of 4,832 | 42.8% |
| Lemmas with more than one **head category** | **416 of 4,832** | **8.6%** |
| Lemmas with **exactly one** head category | **4,416** | **91.4%** |

Categories per form: `1 → 4,416 · 2 → 391 · 3 → 18 · 4 → 3 · 5 → 3 · 7 → 1`.
Of the 416 ambiguous forms, 227 have a category holding ≥80% of their
occurrences.

**This is why v08.21's conclusion was wrong.** v08.21 read the 2,067 figure —
the raw-string count — and concluded that `pos` classifies a written token
rather than a dictionary form, so no category could be shown. The 2,067 is
almost entirely *attached particles varying*, not the word's own class
changing. Once the clitics are accounted for, nine forms in ten have exactly
one category. Genuine ambiguity does exist and is real linguistic ambiguity,
e.g. `رَّحِيم` {Adjective 112, Noun 4}, `يَوْم` {Noun 324, Time Adverb 81},
`ٱلَّذِى` {Relative Pronoun 1442, Conditional 22}.

**How the UI handles it:** the dominant category is shown, a `+n` marker is
placed beside it, and its `title` lists the others. A note under the list says
how many forms in *that list* carry more than one. Nothing is flattened and
nothing is hidden.

### D. Can multiple distinct written forms share the same POS?

**Yes, and it is the normal case.** 2,881 distinct lemmas are Nouns; 1,461 are
Verbs. Within a single root it is routine — root `حمد` has five forms:

| Form | Category |
|---|---|
| `حَمْد` | Noun |
| `حَٰمِدُون` | Noun |
| `مَّحْمُود` | Noun |
| `حَمِيد` | Adjective |
| `يُحْمَدُ` | Verb |

Three Nouns, and they must remain **three separate rows**. A checked-in test
(`two distinct written forms sharing a category stay two rows`) guards exactly
this, using a fixture whose two forms are both Nouns on purpose.

### E. How attached particles affect the classification

They are what makes the raw `pos` misleading, and they are the whole reason
v08.21 concluded no category was available.

`ٱلْحَمْدُ` is recorded as `Determiner + Noun` — the `ٱل` is a separate segment.
The same lemma elsewhere appears as `Noun`, `Preposition + Noun`, `Conjunction
+ Noun`, and so on. Reading the raw string, the form looks like it belongs to
four different categories; it is one Noun wearing four different sets of
clitics.

Stripping to the head resolves this, and the size of the effect is the
2,067 → 416 drop in section C.

### The limitation, reported rather than papered over

Of the 46 segments, **11 are opaque corpus abbreviations the packaged data
never expands**, plus one single-occurrence tagging glitch:

| Tag | Occurrences | Tag | Occurrences |
|---|---|---|---|
| `RES` | 551 | `EXH` | 40 |
| `PRO` | 333 | `SUR` | 35 |
| `PREV` | 161 | `AVR` | 33 |
| `IMPV` | 78 | `EQ` | 6 |
| `EXL` | 66 | `COM` | 3 |
| `INT` | 51 | `yaAsiyna` | 1 |

Together ~1,358 of 77,429 occurrences (**~1.8%**).

Their meanings are *not* in the packaged data. Guessing a grammatical name
from three letters would be exactly the fabrication the instruction forbids,
so **they are printed verbatim, in both languages, and given no Bangla.** A
checked-in test asserts that no Bangla exists for any of them — the absence is
enforced, not merely left undone.

## 5. Correction 2 — the meaning of "Form" corrected

**`Form 1`, `Form 2`, `Form 3` are gone from the user interface entirely**, in
both Basic and Depth, in both languages. The translation key `"Form {n}"` is
removed from `bn.js`, and the label is removed from the renderer's defaults, so
there is no path by which such a string can reach the screen.

Each row now names the **actual grammatical category** the data supplies for
that written form — `Noun`, `Verb`, `Adjective`, `Time Adverb`, and so on.

**Distinct forms sharing a category are not collapsed.** Rows are keyed by

The two v08.21 explanatory notes were **verified against the data before being
touched**, not deleted on sight:

| Note | Verdict | Action |
|---|---|---|
| "The number is this form's position in the list below, not the traditional Arabic verb form (I, II, III…)." | Explains a number that no longer exists | Removed |
| "A grammatical category is not shown per form: …" | **Factually wrong** — the category *is* derivable (section C) | Replaced with "Each form's category is the one the packaged grammatical analysis records for that written form." |

recorded with more than one category; the most frequent is shown."

## 6. Correction 3 — Basic card row layout

Required: `[FORM/POS NAME] [ARABIC WORD] ........ [N OCCURRENCES]`

**A real CSS defect was found and is the root cause.** v08.21 gave this rule to
the row's own label span as well as to the toggle:

```css
.word-card-form-toggle,
.word-card-form > .word-card-form-n { … width: 100%; … }
```

In the Basic tab the row has no toggle and the `<li>` itself is the flex row —
so the *label* claimed the full width, and the Arabic and the count were pushed
out to the far edge. That is the stretching, in CSS. The label is no longer a
row container, and the Arabic went from `flex: 1 1 auto` (which made it absorb
all spare width) to `flex: 0 0 auto`. Only the count is pushed right, by its own
`margin-inline-start: auto`.

**Measured on the rendered page at 1280px** (English, root `سمو`):

| Element | Left | Right |
|---|---|---|
| Category | 203 | 236 |
| Arabic | 244 | 306 |
| Count | 986 | 1079 |
| Expand caret | 1087 | 1095 |

The category and the Arabic are **8px apart**. The count is hard right. The
Arabic is intrinsically sized.

Also asserted, at 1280px and 390px, in both languages: Arabic font size is at
least 1.4× the label beside it; no row overflows the card; no sideways page
scroll on a phone; the category wraps rather than pushing anything off-screen at
narrow widths.

## 8. Correction 5 — the Word Card no longer overlays the āyah

**The defect:** v08.20 kept the card open at the destination and carried the way
back inside the card's own header. So the card sat over the āyah the reader had
asked to see.

**The fix, and what it deliberately does not do:** the card is now *closed* on
the way out — but **its state is not destroyed**. Before navigating, a full
origin record is taken:

```
{ occurrenceId, ref, surah, ayah, stageView, unitType, level, expandedForm, scrollY }
```

`closeWordCard()` also preserves the state object itself (level and occurrence
survive a close, by design since Phase 2). The card is hidden, the āyah is
displayed, and nothing overlays it.

**Verified by geometry, not by an element's absence:** the acceptance run
computes the card's bounding box against `#ayahPanels` and asserts the two
rectangles do not intersect, *and* that computed `display` is `none` for both
mounts — the standing rule about `[hidden]` being overruled by a class rule.

## 9. Correction 6 — the deliberate "← Back to Word Card" control

A new control, `#wordCardReturnBar`, sits on the study screen **above the āyah
and outside the card**. It carries the same `data-word-card-origin-back`
identity the v08.20 control had, so the existing handler and every existing
assertion keep working — this is a relocation, not a replacement.

Pressing it restores, in one action:

- the original word (its permanent occurrence id)
- the study view it was read in (Read or Note)
- the Study Unit type in force at the time
- the Word Card level (WbW / Basic / **Depth**)
- the expanded form **with its occurrence list populated**
- the scroll position

The expanded form is re-opened inside `hydrateWordCardOccurrences()`, where the
forms index actually lands — asking earlier leaves a row reading
`aria-expanded="true"` with nothing under it, which is a real defect this
project has already shipped once.

## 10. Correction 7 — navigation safety

**The control appears only when the āyah was reached from the Word Card.** An
origin record is written in exactly one place, `goToWordOccurrence()`. Ordinary
Study or Note navigation never writes one, and the bar renders nothing without
one.

Asserted on the live page before any word is ever opened: the bar exists, is
`hidden`, and computes to `display: none`.

The origin is cleared — and the bar re-rendered away — when the reader opens any
word directly, or closes the card. Only the **first** hop records an origin, so
a chain of jumps always returns to the word the reader actually started from.

**Card → Āyah A → Back → Āyah B → Back** was run end to end at three
viewport/language combinations. The second hop closes the card and offers Back
again; the second Back returns to the *same* original word.

## 13. Flagged, not changed

**A pre-existing data-notation issue in the packaged lemma text.** 262 of the
4,832 lemmas (**5.4%**) carry a `^`, a `#` or a digit inside the Arabic — e.g.
`ا^بَاء`, `سَمَا^ء`, `ـ#َٰن`, `مَٰلِك2`. Verified against the written text: `ا^`
corresponds to `ءَا` (the madda-alef sequence) at every occurrence checked, and
the digit is a homograph disambiguator.

On screen this reads as corrupted Arabic. **It is not this tranche's doing** —
it has been visible in the Basic card's Lemma line since Phase 2 and in the form
list since v08.21 — and it is **deliberately not changed here**, because
correcting it means transforming the packaged corpus's own text, which is a data
decision for the Owner, not a layout correction. Raised for a decision; the fix,
if wanted, is a normalisation step in the data-pull tool with its own
verification.

**The eleven opaque POS abbreviations** (section 3) are shown verbatim. If their
expansion can be supplied from an authoritative source, they become ordinary
translatable categories with no code change beyond the catalogue.

**One new on-demand fetch.** `lemma-pos-index.json` (159KB) is fetched the first
time a root's derived forms are shown, alongside the two indexes that path
already loads, and cached thereafter. **Nothing joined the startup path (I9);**
the load-speed contract is untouched.
