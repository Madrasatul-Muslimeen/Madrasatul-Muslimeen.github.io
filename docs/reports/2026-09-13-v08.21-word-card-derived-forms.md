> **Surface Token ≠ Lemma ≠ Root ≠ Grammatical Family**

**root** groups, a **lemma** is a derived form, and the **surface token** is

## 2. What the data can and cannot support — measured first

This round's instruction was explicit that a count or classification the data
cannot support must be reported, not invented. So the packaged corpus was
measured before any UI was designed.

### Supported, exactly

| Question | Finding |
|---|---|
| Do root occurrences map to lemmas? | **All of them.** 49,971 root-bearing occurrences, **0 unmapped**. |
| Can one lemma belong to two roots? | **No.** 0 of 4,657 lemmas span more than one root — it is a strict function. |
| How many forms does a root have? | **1 to 22**, median 2. A compact, listable set. |
| Do the numbers add up? | Verified per root: `sum(form counts) + unclassified === root total`. |

So **root → derived forms, each with an exact occurrence count, is fully
supported**, and the totals are real counts rather than estimates.

### NOT supported — and therefore not shown

**A grammatical category per form.** The packaged `pos` field does not
classify a dictionary form. It describes a *written token together with
whatever particles and pronouns are attached to it* — 359 distinct values such
as `"Determiner + Noun"`, `"Conjunction + Verb + Pronoun"`,
`"Preposition + Proper Noun"`. Measured across the corpus, **2,067 of 4,832
lemmas carry more than one `pos` value**: `رَّحِيم` alone appears as
`Adjective`, `Determiner + Adjective`, `Determiner + Noun` and `Noun`.

Labelling a form "Noun" or "Verb" from that data would be inventing a
classification the source does not make. **The card therefore prints no
category per form**, and says so on screen in both languages rather than
leaving a silent gap.

## 3. What was built

### 3.1 Basic Arabic — summary only

Below the existing Lemma / Root / Part of speech list (the selected word's own
data, unchanged), Basic now shows:

- **`{total} occurrences in {forms} derived forms`** — both exact.
- A numbered list, one row per form: **`Form n` — the Arabic form — `{count} occurrences`**.
- Two honest notes: that the number is a **list position, not the traditional
  Arabic verb form (I, II, III…)**, and why no per-form category is shown.
- An explicit line if any of the root's occurrences are unassigned in the data.

**The detailed occurrence lists are gone from Basic**, as instructed. Basic now
renders zero `data-word-occurrence-goto` controls — asserted, not assumed.

### 3.2 Arabic in Depth — same forms, same order, expandable

The **same list in the same order** (count descending, then the lemma itself —
deterministic, so the two tabs can never disagree). Each row is a real
expander.

Expanding one reveals its occurrences, and each occurrence shows **the exact
Arabic word as written at that location** plus its `surah:ayah:position`
reference. This is the part the locked distinction matters for, and it is
visible in the verified output: the one form رَحِمَ/حَمْد family renders as
**ٱلْحَمْدُ** at 1:2:1, **بِحَمْدِكَ** at 2:30:20, **وَٱلْحَمْدُ** at 6:45 —
genuinely different surface tokens, each read from its own surah's data.

Each occurrence opens that āyah. **Back to Word Card** then restores the
original word, **the Depth tab, and the form that was expanded**, plus the
prior Study context (surah, āyah, unit type, and which stage view the reader
was in).

**Ordering, as instructed:** the occurrence section comes first; the semantic
range and dictionary link follow it in `.word-card-depth-rest`, functionality
preserved.

### 3.3 Presentation

Arabic is deliberately much larger than the surrounding English: the card body
runs at 0.9rem, a form's Arabic at **1.5rem (~1.7×)** and an occurrence's at
**1.35rem (~1.5×)**, stepping down at ≤380px. Asserted by measuring computed
font sizes against the panel's own, not by eye. Every row is a ≥44px target.
All 14 new strings are translated; counts render in Bengali digits on a Bangla
page while references keep plain digits.

## 4. A real defect of this round's own

**`ReferenceError: expandWordForm is not defined`** — the expand/collapse
functions were placed inside the `["readView","noteView"].forEach(...)`
callback, so the click handler inside the same closure could see them while
`hydrateWordCardOccurrences()` could not. The visible symptom was narrow and
misleading: expanding a form by hand worked perfectly, but **Back to Word Card
restored a row that said "expanded" with nothing under it**. Found by probing
the live console rather than by re-reading the code; fixed by moving both
functions to module scope.

That is also why the restore is now performed **where the data lands** (inside
the hydrate, once the forms index resolves) rather than at the call site: the
index resolves after the card first paints, so any caller asking earlier finds
no form yet.

## 6. Limits, stated rather than hidden

- **No grammatical category per form** — see §2. The reason is printed on the
  card in both languages.
- **A form's occurrence list is capped at 50**, because each occurrence needs
  its own surah's data to read the word as written there. When a form has more,
  the card says **"Showing the first N of M occurrences"** rather than
  truncating silently.
- **Roots absent from the packaged index** show the existing "Root unavailable
  in the approved dataset" message; 27,458 of 77,429 words have no root at all.
- **Tracking was left in the Word-by-Word tab, where it already lives.** The
  instruction to put "dictionary information, tracking, and the other existing
  Depth details after the occurrence section" was read as ordering *within*
  Depth; tracking is not currently a Depth control, and moving it would remove
  it from where it is verified today. Flagged for the Owner rather than
  decided unilaterally.
