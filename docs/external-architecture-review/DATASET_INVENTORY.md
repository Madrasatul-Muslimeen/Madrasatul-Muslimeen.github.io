# DATASET_INVENTORY.md

Inventory of the Quran datasets QuranRevival v08.00 depends on. **The full data
is 31 MB and is not duplicated into this package.** Small files are copied into
`code/tools/quran-data-pull/output/`; large ones are documented here with real
sample records taken directly from the files.

All sizes and record counts were measured, not quoted.

---

## Location and access

```
Repository path : tools/quran-data-pull/output/
Served at       : /tools/quran-data-pull/output   (BASE_URL in app/js/quran-data.js)
Access          : static HTTP files. NEVER Firestore.
Generated by    : tools/quran-data-pull/pull.js  (+ build-{juz,hizb,page,search}-index.js)
Total size      : 31 MB
```

Architecture s5: *"Quran content is served as static files, one per surah,
cached permanently by the browser — never as Firestore reads."*

## 1. `surahs/surah_001.json` … `surah_114.json` — **ESSENTIAL**

| | |
|---|---|
| **Path** | `tools/quran-data-pull/output/surahs/surah_NNN.json` |
| **Size** | **27 MB** total, 114 files. Smallest 12,305 B (surah 1); largest 2,122,817 B (surah 2) |
| **Format** | JSON, one object per surah |
| **Records** | 114 surahs · **6,236 ayahs** · **77,429 word occurrences** |
| **In this package** | ✅ `surah_001.json` **in full** (12 KB) · ✅ `surah_002_EXTRACT.json` (ayahs 1–3 and 255 only) |

### Schema

```
{ surahNumber, surahNameArabic, surahNameEnglish, surahNameTranslation,
  revelationType, ayahCount,
  ayahs: [ { ayah, uthmaniText, tajweedText,
             translations: { en, bn },
             juz, page, ruku, manzil, hizbQuarter, sajda,
             words: [ { position, arabic, transliteration,
                        translation: { en, bn },
                        morphology: { root, lemma, pos, rootCount } } ] } ] }
```

### Sample record — real, unedited (`surah_001.json`, ayah 1, word 1)

```json
{
  "position": 1,
  "arabic": "بِسْمِ",
  "transliteration": "bis'mi",
  "translation": { "en": "In (the) name", "bn": "নামে" },
  "morphology": { "root": "سمو", "lemma": "ٱسْم", "pos": "Preposition + Noun", "rootCount": 381 }
}
```

### Identifiers

| Field | Scope | Notes |
|---|---|---|
| `surahNumber` | global, 1–114 | |
| `ayah` | **within its surah**, 1-based | not globally unique |
| `position` | **within its ayah**, 1-based | **not globally unique** — verified: zero duplicates within any ayah, but position 1 exists 6,236 times |
| **a global word id** | — | **DOES NOT EXIST.** The address is the triple `(surahNumber, ayah, position)`, never materialised as a key |

### Relationships to other data

- `ayahs[].juz / page / ruku / manzil / hizbQuarter` are the **raw source** the
  four boundary index files below were computed from.
- **`ruku` is a GLOBAL sequential index**, but unit keys store a per-surah index
  — converted by `rukuIndexInSurah()` (`app/js/unit-keys.js:53`). A trap.
- `morphology.rootCount` is a whole-Quran root count, **computed on a merged
  key** — see §7.

## 6. `search-en.json` / `search-ar.json` / `search-bn.json` — NOT essential

| | |
|---|---|
| **Sizes** | en **896 KB** · ar **1.4 MB** · bn **2.1 MB** |
| **Records** | **6,236 each** — one row per ayah |
| **Why not copied** | 4.4 MB combined; ayah-level text search, unrelated to word learning |

```json
{ "lang": "en", "count": 6236,
  "refs":  [1001, 1002, 1003, …],
  "texts": ["In the name of Allah, the Entirely Merciful, the Especially Merciful.", …] }
```

**`refs` uses a packed integer reference: `surah * 1000 + ayah`.** So `1001` is
Surah 1 Ayah 1 and `2255` is Surah 2 Ayah 255. Two parallel arrays, index-aligned.

**Worth noting as precedent:** this is the project's existing pattern for a
generated, lazily-loaded, non-startup-path index — the closest model for the
word/root/lemma index that Documents 7 and 8 identify as missing. It is fetched
only on first search, and only for the language typed in.

| | |
|---|---|
| **Size** | 4 KB |

```json
{
  "generatedAt": "2026-08-01T02:04:14.922Z",
  "schemaVersion": 1,
  "range": { "start": 1, "end": 114 },
  "surahCount": 114,
  "totalAyahs": 6236,
  "totalWords": 77429,
  "wordsWithRoot": 49971,
  "morphology": { "chapterCount": 114, "rowCount": 128011 },
  "sources": [ … three sources … ],
  "failures": []
}
```

**Two figures here deserve the reviewer's attention:**

1. **`totalWords: 77429` and `wordsWithRoot: 49971` were both independently
   verified against the real files and are exactly correct.**
2. **`morphology.rowCount: 128011`** — the 2011 Quranic Arabic Corpus supplied
   **128,011 morphology segments** for these 77,429 word tokens. **`pull.js`
   extracts only root, lemma and POS and discards the rest** (`pull.js:206–215`).
   The grammatical features Level 3 needs — case, mood, voice, verb form,
   person/number/gender — **were in the source and were dropped.** Recovering
   them is a re-pull with a wider extraction, not a search for a new source.

**Every existing index is ayah-level or coarser. There is no word-level index of
any kind.** This is the single most significant missing artefact for the planned
feature: without it, mapping a learning item to its occurrence count at runtime
requires loading all 114 surah files (27 MB), which the load-speed contract
explicitly forbids ("Never load the Quran").

## 9. Data-quality findings

Reported in full because they would otherwise be discovered late.

**(a) `rootCount` merges weak-final-radical roots.** `canonicalRootKey()`
(`pull.js:90`) replaces a final `و`/`ي` with `#` **for counting only**. **19
roots have a `rootCount` disagreeing with their own in-file frequency; 16 are
exactly explained by this merge** (e.g. صلو occurs 99 times, `rootCount` 124 =
the merged صل# group). **`rootCount` is a display figure, not an arithmetic
primitive — do not sum it.**

**(b) Three unexplained residuals:** منن (30 vs 27), امم (118 vs 119), علو (71 vs 70).

**(c) Unicode normalisation is not applied anywhere.** 8 surface-form pairs
differ only in combining-mark order (shadda before/after kasra). **Raw string
equality fails on them; NFC succeeds.** Any word-matching code must normalise.

**(d) The English word-by-word gloss is contextual, not lexical.** **73.8% of
word occurrences (57,146 of 77,429) have a surface form glossed more than one
way** somewhere in the Quran; مِن alone has **72** distinct glosses. **The gloss
cannot serve as word identity.** Root (0.0% ambiguous) and lemma (0.4%) can.

**(e) One malformed POS value** — Surah 37:130 position 3, `"pos": "yaAsiyna"`,
a Buckwalter fragment rather than a tag. 1 word in 77,429; renders harmlessly.
The Bangla gloss on the same word carries a stray `"`.

**(f) Coverage ceilings.** Root data covers only **64.5%** of words — particles
and pronouns genuinely have no root. Lemma reaches **95.7%**.

## 10. Re-pull risk

`pull.js` regenerates all 114 files from three live upstream APIs. **If a re-pull
changes tokenisation, every stored word-level unit key would silently become
wrong** — and I5 requires unit keys to be permanent. The dataset carries **no
per-word version stamp**; `manifest.json`'s `generatedAt` + `schemaVersion: 1`
are the only versioning available.

**Any word-level identity scheme should be pinned to a dataset version, and a
re-pull should be treated as a migration event.**
