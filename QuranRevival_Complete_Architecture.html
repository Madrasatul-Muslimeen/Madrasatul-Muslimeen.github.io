The shape of the whole thing

One platform. Any number of study modules, three account types, six roles. The whole design exists to stop those multiplying into dozens of special cases.

What you study — modules

QuranRevival, Arabic, Hadith, Deen Study, Learn Deen On-the-Go, General Study, Health, Nature-Life — and any number more. Modules are rows of data, not code.

Whose account — tenant type

Individual, Family, Tuition Provider. A madrasah is not a fourth type — it is a Tuition Provider using more of the app.

The separation that makes it work

A module never asks what kind of account it is in. An account never asks which modules are on. Everything else in this document follows from holding that line.

Naming

QuranRevival is a module, not the platform. The platform carries its own name (Madrasatul Muslimeen proposed) in a separate field, so either can be renamed at any time without touching code.

Why 3.5, 5 and 6 are reserved rather than ignored

A medication is not a status between 0 and 5. A payment needs an audit trail. Naming them now means Layer 2 is never bent to hold them later.

The invariants

The short list of rules that keep this from collapsing back into special cases. If these hold, the architecture holds.

#RuleWhat breaks if it is broken
I1Nothing in Layer 2 or 3 ever requires a classIdFamily and Individual accounts stop working. Private tuition cannot take attendance.
I2Modules never call each other. Renderers are shared components.The old syncWayToTracker bridge returns.
I3viaProgramId and viaSessionId live on activity, never in a record keyThree entry paths create three progress states for one ayah; program history overwrites itself.
I4Nothing is ever deleted — archive, revoke, return, mark consumedHistory is lost and cannot be recovered.
I5Units are keyed by permanent ID, never by nameRenaming a topic erases every record attached to it.
I6Confirmation state is frozen when marked, never recalculatedAn independent student joining a madrasah has years of work retroactively un-confirmed.
I7Not Applicable is excluded from totals, not counted as zeroStudents are permanently penalised for approaches that never applied to them.
I8Curriculum content is separate from scheduleA unit cannot be moved between weeks; every class needs its own copy of the curriculum.
I9Nothing joins the startup path without being flaggedThe app gets slower with every module added, permanently.
I10platformAdmin cannot be self-grantedThis is exactly the S1 vulnerability that was found and fixed.
I11Every user-visible name is language-keyed from day oneAdding Bangla later means touching every screen and every record.
I12Roll-ups count through ancestorIds — counted once, never twiceMark Fiqh and Deen Study counts it twice.
I13Tenant isolation is enforced in security rules, not only in queriesA filter in JavaScript is a convenience, not a protection.
I15A failed write must reach the user. Never console.error alone.This is exactly how bug B1 hid: four collections silently failed to save for months while the app looked healthy.
I16Every existing personId is preserved unchanged at migrationstudyProgress, rukuSummaries, juzSummaries, monitorWeeks are all keyed by it. Regenerate one and that person’s entire history is orphaned.
I17Every document carries schemaVersion, createdAt, updatedAt, createdByNo way to change a field safely later; no audit trail for who did what.
I14Sessions are fetched by date range only, never as a setTens of thousands of session documents per school year.

Unit keys are namespaced and permanent

ayah:2:255 range:2:255-257 surah:2 page:madani:127 ruku:2:34 juz:3 hizb:5 rub:20 manzil:2 hadith:bukhari:5678 topic:topic_0042 name:17 (Asma ul Husna)

unitType is stored alongside the key, so “show all page-based progress” is one query.

Layout A — one frame, panels switched on

Each approach declares which tools it needs: text, audio, loop, wordByWord, tajweed, writing, notes, reflection, timer, checklist. Adding approach 31 is a row of data, not a build.

The Guide tab — three fields per approach

What is this approach · How to do it · How to measure your progress. The third is optional with a generic fallback — six statuses × 30 approaches × two languages is 360 short texts, and it must not block the module.

Where Quran content lives — a decision that was missing

Quran text, tajweed markup, word-by-word data and translations are the largest payload in the whole platform — far larger than every record a student will ever create. They are also completely static: ayah 2:255 will never change.

Static content does not belong in a database

Quran content is served as static files, one per surah, cached permanently by the browser — never as Firestore reads. Firestore reads cost money, are slower than a cached file, and buy nothing for data that never changes.

Load one surah when it is opened. Never load the Quran.

The landing rule — computed, not configured

Person uses ONE module -> the app opens straight INTO that module Person uses TWO or more -> card grid + Continue strip

So through Stages A and B almost everyone opens the app and sees the wheel — without the wheel ever being the platform’s front door. As they add a second module the grid appears on its own. Same principle as the adaptive Results view; nothing to configure, nothing to rebuild at Stage C.

The Mastery Wheel is QuranRevival’s landing page, never the platform’s. The approach dropdown sits beside it as a second door — the wheel for seeing everything at once, the dropdown for reaching an approach by name.

Status colours

Six statuses need six steps on the ramp. Achieved and Mastered must be visibly distinct — adjacent colours are indistinguishable on a small wheel segment. Not Applicable is not on the ramp at all: rendered greyed or hatched, and excluded from the total.

Progress statuses

Not Applicable | Not started | Learning | Practising | Achieved | Mastered ^ off the ladder, excluded from totals, rendered greyed/hatched -- never a colour on the ramp

Roles, access and confirmation

RoleCanCannot
ownerCreate the account, add people, invite, configure everything—
primeRun the madrasah academically: all classes, students, teachers, curriculum, reports; confirm anyoneTransfer ownership; Finance
teacherTeach, assign, mark, confirm, reply; edit their own class scheduleRoles, permissions, catalogue configuration; other teachers’ students
guardianAll a teacher can, for their own children only; manage children’s accountsAnyone else’s children
studentStudy, claim status, bookmark, ask, submit homeworkConfirm own attainment; see others
selfStudy and confirm own progress—

Roles are rows. One person may hold several at once — owner + prime + teacher, or owner + guardian + student. platformAdmin sits outside the six, has full access to all accounts and data, and cannot be self-granted. “View as” lets Admin preview the app exactly as a teacher or student sees it.

Who confirms — computed, never configured

Does this person have a teacher, guardian or prime? YES -> their marks wait for confirmation NO -> their marks count straight away

A teacher’s own study is self-confirmed. Confirmation can be switched on or off per subject. Bulk confirm — a surah, a week, a class — is required from the first version, not added later.

Child safety — keyed on isMinor, not on role

  • Minor: guardian sees every thread · no private adult↔child thread · append-only
  • Adult: private teacher↔student thread allowed · still append-only
  • Teacher feedback reaches the parent, copied to Admin

Phase 5 has no checklist source — and needs one

The original plan derived the parity checklist from QuranRevival_System_Blueprint.md. That file was never supplied. So the gate that protects the old app currently has no authoritative list behind it.

Resolution: at the start of Phase 5, the checklist is generated by auditing the live production file directly — every screen, control and stored field enumerated from the code, not from memory or from a document that does not exist. That list is then signed by the owner.

Rules the audit found missing

QuestionRule
Offline conflict — two devices change the same thing while offlineLast write wins on reconnect. Acceptable for study data; the user is told when a value was replaced, never silently overwritten.
Week boundary — when does a week start?Set per tenant, not globally. A madrasah week and a family week are not the same, and every weekly report depends on it.
Migration namingEach existing teacher becomes one tenant, auto-named “<Teacher’s name’s> Madrasah”, editable afterwards.
Backup — separate from exportExport is data portability for the owner. Backup is disaster recovery for the platform. Both needed; they are not the same feature.
Unresolved — needs the owner’s decision

“Nothing is ever deleted” (I4) will one day meet a parent who asks for their child’s data to be removed. A school holding children’s records cannot simply refuse.

These two principles genuinely conflict, and the conflict has not been resolved. The usual answer is anonymise rather than delete — strip the name and contact details, keep the study history detached from any identity. That satisfies both, but it is a decision, not a detail.

Self-check screen — recommended addition

The owner is a non-coder and has already found step-by-step browser testing too laborious to sustain. Every phase that ends with “please test this” is a phase whose verification may not happen.

Proposal: an Admin-only screen that checks the app’s own health — every collection reachable, a test write to each succeeding, no queued offline writes stuck, no silent failures in the last session. One tap, plain-language result.

Bug B1 would have been caught on day one by a screen like this.

Phase 5 is the gate

The old production file is not retired until the parity checklist is signed by you. Until then it remains the live fallback, untouched.

Every feature carries a permanent ID

The same ID appears in this document, in the build step that delivers it, in the parity checklist, and in the About screen inside the app — which reads the same registry and shows each feature as Built or Planned. A feature cannot exist in words only, because the app itself would report it as unbuilt.

Measured against today

The current app makes four failing, blocking round-trips at every startup before it can finish loading. Removing those alone means the new build starts faster than the old one, before any other improvement is counted.

Growth seams

Where the future plugs in without rework. This is the test of whether the architecture holds.

To add…What it costs
A new moduleOne row in modules, if it uses an existing renderer
A new approach (31st, 40th)One row in trackables with its panel list
A new unit typeA new namespace prefix; unitType already stored
A new subject, domain, or levelOne node; re-parent freely, history follows the ID
A new languageA new key inside existing {lang} objects
A new roleOne value; roles are already rows, one person may hold many
A new tenant typeNothing in Layers 2–3 branches on tenant type
A new rendererOnly if a module genuinely needs a fourth kind of screen
Operations, Finance, FacilitiesNew layers alongside; no existing collection changes
The real test

Every row above costs data, not code. Where a row costs a build, that is where the architecture would need revisiting — and there are only two: a fourth renderer, and a new layer.
